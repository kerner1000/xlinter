# 2026-11-10 - Releases 0.3.1 and 0.4.0

## Release

**Done:** xlinter 0.3.1 and 0.4.0 are on npm, the first versions to go through the release workflow from
issue #9. Tag `v0.3.1` names `7e7fafa`, the last commit before PR #22, so 0.3.1 ships the PR #19 change
without the breaking one. Tag `v0.4.0` names `0944b42`. npm records the versions as published at
2026-11-10 06:06:20 and 06:06:40 UTC, and `latest` is 0.4.0. Each provenance attestation names its tag and
commit, while `gitHead` stays empty, as it was for 0.3.0.

**How it went:** Both runs started on 2026-11-09. `build` passed in both, so the source gate accepted both
commits. `publish` failed in both with `ENEEDAUTH`, with `id-token: write` set and npm 11.19.1, so npm
obtained no OIDC token and nothing was staged. Rerunning only the failed `publish` jobs on 2026-11-10
staged both versions with tag `latest`, reusing the tarballs from the first attempts. The state of the
trusted publisher before the rerun was not recorded, so whether it had expired is unconfirmed.

`npm stage download` returned `E401` with the token in `~/.npmrc`, while `npm whoami` accepted the same
token. `npm stage approve` authenticated through a browser login with 2FA instead. The first approval of
0.3.1 returned `E409` because npm's automated review had not finished, and a retry minutes later
succeeded. 0.3.1 was approved before 0.4.0, and after each approval `latest` named the approved version.

**Decided:** The `Releasing` section of `AGENTS.md` now covers the `ENEEDAUTH` rerun, the `E401` fallback,
browser approval, `E409`, approval order, a provenance check that prints the commit, and the gate's lack
of a version check.

**Resolved from the 2026-11-09 entry:** 0.3.1 was released from `7e7fafa`. The trusted publisher works.
